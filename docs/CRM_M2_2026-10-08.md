# Offline M2 evidence — persistent reusable CRM

The contacts/activity/follow-up slice now runs through one shared service/API and
dashboard in hospitality and professional-service references. Both independently
installed consumers use identical compiled CRM/adapter artifacts. The Archava core
has no mandatory CRM dependency. Instructions and release boundaries are in
[CRM module](CRM_MODULE.md).

Delivered contracts cover strict data validation, pagination/search, create/update
contacts, immutable activities and follow-up create/complete. PostgreSQL owns the
records, tenant memberships and metadata audit. Permission checks, assigned-record
scope, forced tenant RLS and composite foreign keys enforce isolation. Revision
preconditions handle concurrent changes. Opaque command ids and stable server HMAC
fingerprints preserve retry identity; record, receipt and audit commit atomically.

The read/draft tool allowlist accesses the same authorized service. Machine reads
intersect machine/initiator grants. Machine mutations are refused until verified
Act integration exists; preparing a follow-up creates only a revision-bound draft.
The dashboard operates without an LLM and stores no business data in localStorage.

Checks use Node 22.22.3, pnpm 10.15.1 and real PostgreSQL 18.6 in an isolated
Unix-socket cluster. The backend verifier uses plain Node with installed public
exports; it refuses workspace-source resolution. Membership locking uses a
tenant-checked read function so the application role receives no membership UPDATE
rights. Initial migration/re-entry with existing data is verified; later schema
upgrade, backup restoration and production identity are separate requirements.

A deliberate viewer command returns HTTP 403 in browser verification.
No unexpected browser exceptions/resources failed. These are local reference
accounts, not production SSO/login evidence.
